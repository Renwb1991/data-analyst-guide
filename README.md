## 三个设计原则

### 1. 所有示例基于同一套数据表

全篇不换数据集，每个例子都能算出具体数字，而不是抽象讲道理。

| 表 | 粒度 | 用途 |
|---|---|---|
| `dim_user` | 一个用户一行 | 维度表、NULL 陷阱、LEFT JOIN 退化 |
| `dwd_order` | 一个订单一行 | 事实表、聚合、窗口函数 |
| `dwd_order_item` | 一个订单的一个商品一行 | **JOIN 膨胀演示** |
| `dwd_event` | 一次事件一行 | 窗口函数、路径分析、JSON 解析 |
| `ods_fe_event` | 一次前端事件一行 | 埋点、前后端匹配率 |
| `dwd_exp_assignment` | 一个用户在一个实验里一行 | A/B 实验分流与 SRM |
| `dws_city_daily` | 一个城市一天一行 | DID、合成控制 |
| `dwd_llm_eval` | 一条评测样本一行 | LLM 评测、Judge 一致率 |

数据是刻意构造的。举几个例子：

- `user_4` 注册但零订单、且 `city` 为 NULL → 演示 LEFT JOIN 被 WHERE 打回 INNER、以及 `!=` 遇 NULL 静默丢数据
- `O1` 在明细表有两行 → 演示 JOIN 粒度膨胀
- `O1` 和 `O4` 金额都是 200 → **专门用来证伪 `SUM(DISTINCT)` 这个常见的错误解法**
- 订单日期跳过了 09-02 和 09-04 → 演示日期补零、以及 `LAG` 跨过缺失日期导致环比算错

所以 1.3 节能摆出三个数字：真实总额 **1050**，错误 JOIN 得 **1250**，加 `DISTINCT`「修复」后得 **850** —— 一眼看懂为什么 DISTINCT 不是解药。

### 2. 每个坑都配「错误代码 → 错误结果 → 机制解释 → 两种修法」

不是列举「注意 XX」。先给一段**看起来完全合理**的错误 SQL，展示它算出的错误结果表，解释底层机制，再给修法。

重点展开的几个：

| 陷阱 | 为什么值得单独讲 |
|---|---|
| LEFT JOIN 被 WHERE 打回 INNER | 不报错、结果看着正常，最难发现 |
| 一对多 JOIN 膨胀 | 列为全章最重要一节，含三表连环膨胀 |
| `LAST_VALUE` 默认窗口框架 | 几乎所有人第一次都会踩 |
| `NOT IN` 遇 NULL 返回 0 行 | 结论直接是「把不用 NOT IN 写进个人规范」 |
| `CROSS JOIN UNNEST` 丢弃空数组 | 导致分母偏小、占比虚高，极隐蔽 |
| 分区时区 ≠ 时间戳时区 | 每天静默少 8 小时数据，数字只是「偏低一点」 |
| 用户级分流 + 请求级指标 | 方差低估约 10 倍，大量假阳性 |
| 用「有行为的用户」当实验分母 | 违反 ITT 原则，系统性高估效果 |

### 3. 文中数值全部实算核对

样本量公式、SRM 卡方检验、结构/效率拆解的每个数字都跑过验证。

初稿里有若干处是估算的，核对后发现偏差并已修正。举一个有教学意义的：`srm_check(50300, 49700)` 原本标注「p=0.0031，需要警惕」，实算是 **p=0.058，属于正常**。顺带补了一条关键澄清——

> **同样的比例偏差，样本量越大越可疑。** 10 万样本下 50.3/49.7 完全正常（p=0.058），100 万样本下同样的比例对应 p≈2×10⁻⁹。所以 SRM 必须跑卡方检验，不能靠肉眼看比例。

## 怎么用这份资料

1. **先过一遍[学习清单](./data-analyst-learning-checklist.md)**，把已经掌握的打勾，找出自己的缺口
2. **做对应阶段的「里程碑自测」**——这是开放题，答不出来说明是「看过」不是「会」
3. **缺口对应到正文章节精读**，每节末尾有 `⚠️ 自检`（折叠答案）
4. **用章末的「完成标准」验收**，而不是「读完了」就打勾

> 清单里的勾选框是 Markdown 任务列表，fork 之后直接改 `- [ ]` 为 `- [x]` 即可当作自己的进度表。
